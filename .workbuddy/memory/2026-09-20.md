## 慢 turn 诊断（demo-session-1，只分析未改码）

现象：15:26 起每轮 150-230s（trace 显示值），此前仅 18-47s。

结论（三个叠加原因）：
1. **压缩每轮必触发**：触发条件 `_estimate_tokens_full > MAX_TOKENS(2000)`，但压缩后的稳态地板 = (system ~220 + 摘要 ~250 + recent 800 + 工具定义 755) × 1.5 ≈ 3040 tok > 2000，永远压不回阈值以下 → 死循环。MAX_TURNS=30 实际不参与触发。数值已用项目代码验证。
2. **summary 模型极慢**：`qwen3.8-27b`（DashScope），45-90s/次；total_tokens 8723 但 max_tokens=500 → completion 实为 2000-3000+，疑似默认开 thinking（reasoning 不受 max_tokens 约束）。主模型 qwen3.8-max-0902 同量级 prompt 仅 7-23s。
3. **trace 总耗时重复计数**：summary.create 嵌套在 trim_messages 里，`total_duration_ms` 把两者都加 → 显示 135s 实际墙钟 76s、显示 190s 实际 104s。

放大器：用户因慢重试同一输入 5 次（15:22-16:16）。

修复方向（待用户确认）：阈值须大于压缩后地板（或加滞后/冷却）；摘要关 thinking 或换非思考模型、可移出关键路径；trace 总耗时改墙钟差或只计顶层 step。

## 根因 2 实证（未改码，仅 API 探针）

同一小 prompt 实测（DashScope compatible-mode）：

| 调用 | 耗时 | completion | reasoning_content |
|---|---|---|---|
| qwen3.8-27b 默认 | 8.8s | 160 | 有(178 chars) |
| qwen3.8-27b extra_body={"enable_thinking": False} | 0.9s | 37 | 无 |
| qwen3.8-max-0902 默认（主模型） | 2.6s | 65 | 有(55 chars) |

结论：① 网关 Qwen3 系默认开思考，reasoning 不受 max_tokens 约束；② enable_thinking=False 生效，小 prompt 快 ~10x → 真实 8k prompt 预计 60-90s 降到 5-15s；③ 主模型也带思考（84e6d9a2 里 37s 那次大概率是长思考），是否关闭需权衡质量。

另：`to_summarize` + previous summary 每轮重发，MAX_HISTORY_CHARS=8000 是字符截断而非 token 预算；增量摘要宜按上次压缩点做游标。

环境备忘：venv 内 stdin 脚本调用 `load_dotenv()` 会因 find_dotenv 拿不到 `__file__` 报 AssertionError，须显式 `load_dotenv(".env")`。

## 压缩阈值方案评估（用户提议，未改码）

用户先自己把 `MAX_TOKENS` 2000→3000、`KEEP_RECENT_TOKENS` 800→1500（仅改常量），提议再改成 `MAX_ACTIVE_TOKENS=3000` + `KEEP_RECENT_TOKENS=1200`，触发口径改 `_estimate_tokens(other_msgs)`（不含工具定义、不乘 1.5）。

**本质原因（比"阈值太小"更准确）：上下两个阈值单位不一致。**
- 触发阈值 `_estimate_tokens_full` = (消息原始估算 + 工具定义) × 1.5
- 保留窗口 `KEEP_RECENT_TOKENS` 在 `_recent_msgs` 里比的是 `_estimate_tokens(turn)`，**原始单位无 ×1.5**
→ 天花板被乘 1.5、地板没有，天生不可达。只调常量（2000→3000）反而抬高地板，仍每轮触发。

**实测（demo-session-1 真实 DB）**：全量口径 3435 > 3000（触发）；提案口径 1170 ≤ 3000（不触发）；压缩后水位 = 摘要 353 + recent 1170 = 1523 ≤ 3000 ✓；平均每轮 195 est → 约每 8 轮压缩一次；单轮最大 541 est。
成分实测：工具定义 755 原始（×1.5 = 1132）、persona 12、摘要 353、活跃消息 1170。

**估算器标定**：真实 0.583 token/字符 vs `_estimate_tokens` 假设 0.5 → 只低估 1.17 倍（×1.5 系数过保守）。3000 est ≈ 真实 3500 token。

**两个结构性风险**：
1. `_recent_msgs` 的 `if kept and ...` 保证至少保留最后一个 turn，若单轮自身 > 预算则死循环回归（当前数据最大 541，靠数据巧合安全，非设计保证）。
2. `_estimate_tokens_full`/`_get_tool_def_tokens`/`_TOOL_DEF_TOKENS_CACHE` 会变成死代码，但应保留改作**上下文安全上限**（配合从未被调用的 `_is_context_overflow`）——策略阈值与安全上限职责不同。

另：`test_trim_messages.py` 4 处引用 `agent.MAX_TOKENS`（155/170/190/218）；当前摘要 702 字符，超 prompt 里"不超过 500 字"的要求。

## 压缩阈值三件事已落地

1. **统一口径**：`__init__` 里 `MAX_TOKENS`（3000）改名 `MAX_ACTIVE_TOKENS`，`KEEP_RECENT_TOKENS` 改 1200；`_plan_compaction` 触发改看 `active_tokens = _estimate_tokens(other_msgs)`（原始口径，不含工具定义/persona/摘要），`plan["tokens_before"]` 也改成这个量。
   触发条件是三个独立理由任一成立：活跃超预算 / 轮数超 `MAX_TURNS` / 全量超 `MAX_CONTEXT_TOKENS`。
2. **`_recent_msgs` 硬上限**：新增 `max_turns` 参数（`KEEP_RECENT_TURNS=10`），与 `keep_tokens` 同时生效取先到者，仍保证至少留最后一个 turn。
3. **溢出防线两条路**：
   - 阈值预判：`MAX_CONTEXT_TOKENS=24000`（含工具定义的全量口径），当前实际全量仅 3435，属纯安全网

   - `n_to_sum <= 0` 时新增 warning 日志（"超预算但无历史可压"），把"单轮过大"这个残余风险显性化
